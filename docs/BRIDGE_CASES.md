# 站在一格平台上时，玩家占哪些格 / bridge 该放哪

## 设定

- 平台在 `x=0`，占像素区间 `[0,16)`
- 玩家宽 `W=20px`（`Player.cs:57299`），身体占 `[px, px+19]`
- 列号 `col(v) = floor(v/16)`
- 身体压住的列区间：`lcol = floor(px/16)`，`rcol = floor((px+19)/16)`
- **支撑条件**：`lcol <= 0 <= rcol`（平台那列被身体压住）

20px 宽必然跨 2 列，px 落在特定位置时跨 3 列。

| # | 占据列 | px 范围 | 跨几列 | 平台在身体的 |
|---|--------|---------|--------|-------------|
| A | `[-2, 0]` | -19 .. -17 | 3 | **最右**（边缘） |
| B | `[-1, 0]` | -16 .. -4 | 2 | **最右** |

关键观察：

- **平台列可以在身体的最左、中间、最右三种位置** —— 这就是"同一格平台能算出 3 种 x 坐标"的来源
- A / E 是极端情况：身体只有 1-3px 压在平台上，摇摇欲坠但确实站得住
- C 是唯一平台在正中间的情况，此时身体左右各探出一列

## 二、每种情况下 bridge 该放哪

### 规则前提

1. **锚点接龙**：平台要延伸，新平台必须紧邻已有支撑物（本例中 x=0 的平台，或先前铺的平台）
2. **有背景墙时例外**：背景墙本身就是锚点，可以隔空放
3. **落点必须真的移动**：落点 = 当前格 会被自环过滤器删除

### 判据

设方向 `dir = +1`（往右）或 `-1`（往左）：

```
往右：placeCx = max(baseCol + 1, rcol + 1)
往左：placeCx = min(baseCol - 1, lcol - 1)
```

`baseCol` = 有支撑的那列（本例恒为 0）。

取 `max` / `min` 的原因见下表 C/D/E 三行。

### 逐情况

| # | 占据列 | baseCol+dir (往右) | rcol+1 | **正确 placeCx** | 落点格 | 说明 |
|---|--------|-------------------|--------|-----------------|--------|------|
| A | `[-2,0]` | 1 | 1 | **1** | 1 | 两者一致 |
| B | `[-1,0]` | 1 | 1 | **1** | 1 | 两者一致 |
| C | `[-1,1]` | 1 | 2 | **2** | 2 | ⚠ `baseCol+dir=1` 落在**身体内**，1 已被占 |
| D | `[0,1]` | 1 | 2 | **2** | 2 | ⚠ 同上 |
| E | `[0,2]` | 1 | 3 | **3** | 3 | ⚠ `baseCol+dir=1` 落在身体内，差 2 列 |

往左对称：

| # | 占据列 | baseCol-1 (往左) | lcol-1 | **正确 placeCx** | 落点格 |
|---|--------|------------------|--------|-----------------|--------|
| A | `[-2,0]` | -1 | -3 | **-3** | -3 |
| B | `[-1,0]` | -1 | -2 | **-2** | -2 |
| C | `[-1,1]` | -1 | -2 | **-2** | -2 |
| D | `[0,1]` | -1 | -1 | **-1** | -1 |
| E | `[0,2]` | -1 | -1 | **-1** | -1 |

## 三、为什么 `baseCol + dir` 单独用是错的

C / D / E 三种情况下，`baseCol + dir` 算出的格子**在玩家身体内部**：

```
情况 D：px=0，身体占 [0,1]
        平台在 0
        baseCol + 1 = 1  ← 身体右半边就站在这儿

  列:   -1    0    1    2
       ┌────┬────┬────┬────┐
       │    │████│████│    │   ██ = 身体
       │    │▓▓▓▓│    │    │   ▓▓ = 平台
       └────┴────┴────┴────┘
                  ↑    ↑
            baseCol+1  rcol+1
              (错)     (对)
```

放在 1 的后果：落点 = `(1, footRow-1)`，而玩家本来就站在那儿 → **落点等于当前格** → 自环过滤器删掉这条边 → bridge 候选凭空消失。

在竖井里这是唯一的横向出路，删掉后只剩往上挖 —— 这就是 (608,656) 那次的成因。

---

## 四、`rcol+1` 单独用够不够？

不够，A / B 两种情况会**跳过接龙**：

```
情况 A：px=-19，身体占 [-2,0]
        平台在 0，身体只有右边 3px 压在上面

  列:   -3   -2   -1    0    1
       ┌────┬────┬────┬────┬────┐
       │    │████│████│█▓  │    │
       └────┴────┴────┴────┴────┘
                            ↑
                       rcol+1 = 1 ✓（正好紧邻平台）
```

A / B 往右时 `rcol+1` 恰好等于 `baseCol+1`，所以没问题。但**往左**时：

```
情况 A 往左：lcol-1 = -3
        平台在 0，中间隔着 -1、-2 两格空气
        无背景墙时 -3 放不出来（锚点不相邻）
```

所以 `min(baseCol-1, lcol-1) = -3` 在无背景墙时会失败。

**结论**：取 `max`/`min` 保证不落在身体内，但**不保证锚点相邻**。锚点是否成立要另外判（`CanPlaceReal` / 背景墙）。放不出来时应当回退到"贴着身体最外缘那一格"逐格接龙。

---

## 五、待确认

1. 现有实现只做了「不落在身体内」，**没有**做「锚点不相邻时回退逐格接龙」——A/B 往左、E 往右这类情况可能仍然生成放不出来的边
2. `cur.Px` 是规划器模拟出的浮点位置，和真实玩家可能差一列（日志 `footCols[607..608]` vs 实际 608/609）；上面所有推导以 `cur.Px` 为准，若它本身偏了，结论跟着偏
3. 背景墙在洞穴里几乎处处都有（`wall=64`），所以实际运行中锚点问题可能很少暴露
